# Domain docs

## Before exploring the domain

Read the root `GLOSSARY.md` and any ADRs in `docs/adr/` that cover the area you're working in. If either is absent, continue. The `domain-modeling` skill creates these files when a term or decision is settled.

## Use the glossary's vocabulary

Use glossary terms in issue titles, proposals, hypotheses, and test names. When a concept lacks a definition, check the codebase for established terminology and flag genuine gaps for `domain-modeling`.

## Flag ADR conflicts

If a proposal conflicts with an existing ADR, cite the ADR and explain why the decision is worth reopening.
